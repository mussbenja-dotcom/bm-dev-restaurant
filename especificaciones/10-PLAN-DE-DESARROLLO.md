# Plan de desarrollo y entrega operativa

Claude empieza a programar y pasa por todas las etapas consecutivamente. Resuelve decisiones reversibles con su criterio y usa herramientas gratuitas. Cuando una comprobación falla, diagnostica, corrige y vuelve a probar. Si una dependencia externa queda bloqueada, hace todo el trabajo local e independiente que pueda y registra el obstáculo al entregar.

| Etapa | Desarrollo | Evidencia de terminación |
|---|---|---|
| Base operativa | Arranque local, base persistente, alta del primer administrador, restaurantes, empleados, roles y carta. | Desde una instalación vacía se crean dos restaurantes aislados, con datos propios. |
| Turno completo | Mesas, QR, comandas, cocina, barra, disponibilidad, pagos, cierre y exportación. | Dos sesiones ven el mismo turno, el efectivo cuadra y reiniciar el servidor conserva los datos. |
| Experiencia visual | Carta, salón, cocina y caja con revisión obligatoria en celular, tableta y PC. | Capturas antes/después con tres mejoras concretas, navegación por teclado y legibilidad probada. |
| Módulos gratuitos | Mostrador, retiro, delivery, reservas, recetas, inventario, costos, promociones, proveedores e informes según las especificaciones. | Cada flujo se puede usar con registros persistentes y pruebas repetibles. |
| Entrega local | Configuración, instrucciones, copias, restauración y guía para traslado. | Arranque limpio, prueba en red local si la red lo permite, copia restaurada y build disponible. |

## Condiciones de entrega

Los ejemplos ficticios sirven para validar los mismos flujos que usa el restaurante, en una base separada. Entregar la aplicación tangible, el código, las migraciones, la configuración de ejemplo y evidencia de las pruebas. Si hay un límite de sesión, dejar por escrito lo completado y el próximo paso concreto para retomar la implementación.

La publicación queda para cuando Rubén elija su hosting. El archivo de futuras mejoras enumera las opciones pagas que puede decidir sumar después.
